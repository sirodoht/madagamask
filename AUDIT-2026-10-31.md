# Madagamask security audit

Model: Fable 5.1 high
Date: 2026-10-31
Baseline: commit `78bf1b3` on `main` ("feat: enable Ethereum mainnet signing for small-amount testing")
Scope: `src/`, `manifests/`, `scripts/`, `package.json`, lockfile, `.github/workflows/check.yml`
Method: manual line-by-line review, `npm audit`, the unit suite (54 passing), and two throwaway probes against the real core modules to confirm findings M-1 and L-2. No code in the repository was modified.

This is a code review by one reviewer, not a formal third-party audit, and it does not cover a compromised browser or OS, hardware wallets, or the correctness of viem and noble cryptography.

## Summary

Overall the code is careful. The wallet has a sound trust boundary design: only browser-supplied sender fields authorize messages, the MAIN-world provider holds no secrets, approvals are pinned to payload, origin, document, account, chain and vault epoch, and the vault uses authenticated encryption with correct parameters. I found no way for a website to obtain a signature or account address without the user approving a request, and no DOM injection sinks in the UI.

The findings are mostly about what a user can be tricked into approving, and about operational robustness now that mainnet signing is on.

## Findings

### M-1. A dapp can rewrite the built-in mainnet network (Medium)

**Where:** `src/core/networks.ts:192-211` (`Networks.add`), `src/core/dapps.ts:297-312` and `src/core/dapps.ts:459-470` (`wallet_addEthereumChain`), `src/ui/popup.ts:900-920` (approval card).

**What happens.** `Networks.add` removes any existing item with the same chain ID and appends the new one. It is reached both from Settings and from the dapp method `wallet_addEthereumChain`. Nothing distinguishes the three built-in networks from user-added ones, and nothing checks that the submitted `chainName` or `nativeCurrency.symbol` match what the wallet already knows about that chain ID. The only validation of the RPC URL is that it is HTTPS and that it answers `eth_chainId` with the requested number, which an attacker's server trivially does.

Confirmed with a probe against the real `Wallet` class. After one approved `wallet_addEthereumChain` request from a connected site, the stored entry for chain 1 changed from

```
{ id: 1, name: 'Ethereum', rpc: 'https://ethereum.reth.rs/rpc', symbol: 'ETH' }
```

to

```
{ id: 1, name: 'Sepolia Testnet', rpc: 'https://evil.example/1', symbol: 'SepoliaETH' }
```

**Attack scenario.** A user tries a "testnet" dapp with a key that also holds real ETH, against the README's advice. The dapp sends `wallet_addEthereumChain` with `chainId: "0x1"`, `chainName: "Sepolia Testnet"`, symbol `SepoliaETH` and its own RPC. The approval screen is titled "Add network" and lists `chainId: "0x1"` in hex among other fields. The user approves, then approves a "Switch network" prompt. From then on every screen in the wallet labels real mainnet as "Sepolia Testnet", shows balances in "SepoliaETH" supplied by the attacker's RPC, reports attacker-chosen gas estimates and execution-check results, and the attacker receives every signed raw transaction first. A subsequent `eth_sendTransaction` for "1 SepoliaETH" is a real mainnet transfer. The only remaining defense is the one-line notice "Ethereum mainnet uses real ETH", which the UI shows based on the numeric chain ID.

Even without fund loss, the attacker's RPC can lie about balances and receipts to support off-chain scams, and it sees every address and request the user makes on mainnet.

**Why this matters more now.** Before `78bf1b3`, chain 1 was not in `SIGNING_CHAINS`, so the worst outcome was a lying balance. With mainnet signing enabled the rewritten entry sits directly on the signing path.

**Recommendation.**
1. Treat the built-in networks as immutable from the dapp path. For `wallet_addEthereumChain` with a chain ID the wallet already has, either reject with error 4902-style "already exists" or require the request to match the stored name and symbol and only offer to switch.
2. Allow RPC replacement for a built-in chain only from Settings, with the full URL shown.
3. On the approval screen, render the chain ID in decimal and, for well-known IDs, show the canonical name from viem's chain registry next to the dapp-supplied name, and warn loudly when they differ.
4. Add tests for `wallet_addEthereumChain`: new chain, existing user chain, existing built-in chain, mismatched name.

### M-2. Phishing protection fails open on a single bad feed entry (Medium)

**Where:** `src/core/phishing.ts:12-27` (`parseDomains`), `src/core/phishing.ts:45-64` (`load`), `src/core/dapps.ts:207` and `src/ui/popup.ts:950`.

**What happens.** `parseDomains` throws if any one entry fails the ASCII regex or lacks a dot. In `load`, any throw clears the domain set and sets `updatedAt` to 0. The wallet continues to operate; the approval screen shows "Phishing list: unavailable" in small text. The upstream list is a third-party JSON file of 232,288 entries that the wallet fetches and parses as a whole, and the same parser also gates the bundled snapshot.

Because `update()` writes the raw array to storage only after a successful parse, the live-update path is safe. The problem is `load()`: if the stored snapshot or the bundled file ever contains one entry the regex rejects (a Unicode domain, a wildcard, a stray space), protection is off for every request until the user notices the small-print status and manually updates.

There is also no automatic refresh. The list is marked "stale" after 24 hours, and the only trigger is a button in Settings. A blocklist that is weeks old is close to no blocklist for new phishing sites.

**Recommendation.**
1. Make `parseDomains` skip and count invalid entries instead of rejecting the whole feed, and only fail if the valid count is below a floor (for example 50% of the previous count).
2. Refresh the list on an alarm (daily) when the background wakes, keeping the previous snapshot on failure.
3. When status is `unavailable`, show it as a prominent warning on approval screens rather than small print.

### L-1. Global approval slots can be exhausted by one attacker (Low)

**Where:** `src/core/dapps.ts:233-243`, `src/browser/background.ts:80-109`.

The pending-request cap is eight across all origins and one per origin. Origins include the host, so `a.evil.example` through `h.evil.example` are eight distinct origins. Each may send `eth_requestAccounts` without any prior connection. Each request opens or focuses an approval window and holds its slot for 120 seconds, then can be re-issued. Result: every legitimate site's requests fail with -32002 "A request is already pending" for as long as the attacker's tabs are open, and the extension's approval window keeps appearing. This is an annoyance DoS and a phishing aid (the attacker's "Connect this site?" prompts stay on top).

**Recommendation.** Count pending requests per tab as well as per origin, limit unconnected origins to one `eth_requestAccounts` per tab, and do not raise the approval window for unconnected origins more than once per tab per minute. Consider using the registrable domain (eTLD+1) for the per-site cap.

### L-2. Full key re-derivation on every state poll and dapp request (Low)

**Where:** `src/core/vault.ts:449-480` (`view`), `src/core/vault.ts:171-183` (`signer`), `src/core/dapps.ts:155-163` (`accounts`), `src/ui/popup.ts` 3-second `syncState` poll.

`Vault.view()` calls `signer(data, index)` for every account to compute its address. For mnemonic wallets that means `mnemonicToSeedSync` (PBKDF2-HMAC-SHA512, 2048 rounds) plus BIP-32 derivation plus a secp256k1 scalar multiplication, per account, per call. Measured in the probe:

| Accounts | `view()` time |
| -------- | ------------- |
| 1        | 10 ms         |
| 10       | 96 ms         |
| 30       | 290 ms        |

`view()` is called by the popup every 3 seconds, by the background's epoch watcher, and twice per dapp request through `Dapps.accounts`. Any connected site can issue `eth_accounts` 100 times per minute per tab with no approval. With 30 accounts that is about 29 seconds of background CPU per tab per minute, enough to make approvals and signing sluggish or time out. It also means the private key of every account, not just the selected one, is materialized in memory thousands of times per hour.

**Recommendation.** Cache derived addresses in the in-memory session at unlock time (they are public) and only call `signer()` for the account that is actually signing. Addresses change only on `addAccount`, `addWallet` or migration.

### L-3. Approval screen can be swapped under the cursor (Low)

**Where:** `src/ui/popup.ts:1757-1762` (`home` renders `approvals[0]` in the approval window), `src/ui/popup.ts:1884-1916` (`syncState`).

In the dedicated approval window, `home()` always renders the first pending approval. `syncState` polls every 3 seconds and re-renders when the list of approval IDs changes. If the request being viewed disappears (its tab navigates, it expires, or the site revokes) and another site's request is queued, the window repaints with the second request in the same layout, with the Approve button in the same position. The button handler captures the rendered item, so the user approves what is on screen, but a user mid-click approves something they did not read. Exploiting this needs the attacker to already have a connected second origin with a pending request and to time a navigation within the 3-second poll, so impact is limited.

**Recommendation.** When the viewed approval disappears, show a neutral "Request withdrawn" screen and require an explicit click to view the next request. Disable the Approve button for 500 ms to 1 s after every render of an approval screen.

### L-4. Dapp ERC-20 transfer preview misstates recipient and amount (Low)

**Where:** `src/ui/popup.ts:1129-1162` (`transactionSummary`), `src/core/tokens.ts:203-211` (`interpret`), `src/core/dapps.ts:270-274`.

For a dapp-initiated `eth_sendTransaction` whose calldata is `transfer(to, amount)`, `preview.asset` is undefined because that field is populated only by the wallet's own token-send flow. The summary therefore shows "Recipient: <token contract>" and "Amount: 0 ETH". The actual recipient and amount appear below in a sentence as "request a transfer of 1000000 base units to 0x…", without decimals even when the token is imported. A user who scans the summary rows sees a zero-value transaction to a contract.

**Recommendation.** Populate `asset` from the interpretation when the target is an imported token (decimals and symbol are known), and otherwise promote the decoded recipient and raw amount into the summary rows with an explicit "token base units, decimals unknown" label.

### L-5. Reset leaves non-vault state on disk (Low)

**Where:** `src/core/vault.ts:730-744` (`reset`), `src/core/wallet.ts:225-229`.

Reset removes the vault and clears dapp grants. It does not remove `activity` (transaction hashes, from/to addresses, calldata), `tokens`, `networks` or `phishing`. The UI text says "This removes all local wallets and accounts." A later owner of the profile, or a user who hands over a machine, can recover which addresses were used and what they sent. Custom RPC URLs, which may embed API keys, also survive.

**Recommendation.** Have `reset` clear every wallet-owned key in IndexedDB, or delete the database.

### L-6. PBKDF2 is the weakest defensible KDF choice (Low)

**Where:** `src/core/vault.ts:16`, `src/core/vault.ts:267-290`.

PBKDF2-HMAC-SHA256 at 600,000 iterations matches the OWASP floor, and the implementation is correct (random 32-byte salt, non-extractable material, correct AAD). Still, PBKDF2 has no memory hardness, so a GPU attacker with the ciphertext and a 12-character human password does far better than against scrypt or Argon2id. The dependency tree already contains `@noble/hashes`, which ships both scrypt and Argon2id and is used by viem. The envelope has a version field, so migrating on next unlock is cheap.

**Recommendation.** Add envelope version 2 with scrypt (N=2^17, r=8, p=1) or Argon2id (64 MiB, t=3), and re-encrypt on first successful unlock. Keep v1 read support.

### L-7. CI actions pinned by tag, no local `ignore-scripts` (Low)

**Where:** `.github/workflows/check.yml:9-14`, `.npmrc`.

`actions/checkout@v4`, `actions/setup-node@v4` and `jdx/mise-action@v2` are mutable tags. CI already uses `npm ci --ignore-scripts` and `permissions: contents: read`, which is good, but a compromised action tag could still alter the build that produces the release zips. Locally, `npm install` will run dependency lifecycle scripts because `.npmrc` does not set `ignore-scripts=true`.

**Recommendation.** Pin actions to full commit SHAs with a comment naming the version, and add `ignore-scripts=true` to `.npmrc`. Dependabot or Renovate can keep the SHAs current.

### L-8. Firefox document targeting for provider events is unverified (Low)

**Where:** `src/browser/background.ts:130-136`, `src/browser/background.ts:171`.

`notifySites` sends `accountsChanged` and `chainChanged` to the tab with `{ documentId: site.documentId }`. On Firefox `sender.documentId` falls back to the page URL. I could not confirm from available documentation which Firefox versions honor `documentId` in `tabs.sendMessage` options. If the option is ignored, the message goes to whatever document is now in the tab. The `sites` map is cleared on `tabs.onUpdated` "loading", so the window where a stale entry exists is small, but if it is hit the new origin receives the previous origin's granted address without consent.

**Recommendation.** Pass `frameId: 0` as well, and have the content script ignore `provider:event` messages whose `origin` field (add one) does not equal `location.origin`. Verify Firefox behaviour in the Selenium suite.

### L-9. Token metadata homoglyphs are not caught (Low)

**Where:** `src/core/tokens.ts:34-40` (`metadata`), `src/ui/dom.ts:7-11`.

Control characters and bidi overrides are rejected and bidi characters are escaped at render. Zero-width characters (U+200B to U+200F, U+FEFF) and confusable letters (Cyrillic `С` for Latin `C`) pass. An imported malicious token can therefore display as "USDC" next to the real one. Because token import is user-initiated, exploitation needs the user to paste an attacker-supplied address, which is a common phishing step.

**Recommendation.** Reject `\p{Cf}` and non-ASCII in symbols, and show the contract address alongside the symbol in the token list and send screen.

## Informational

**I-1.** `eth_chainId`, `net_version` and the EIP-6963 announcement are served to any HTTPS page before connection (`src/core/dapps.ts:209-210`). This reveals wallet presence and the selected network, which is standard provider behaviour but worth stating in SECURITY.md.

**I-2.** For connected sites, ten read-only RPC methods are relayed with unvalidated parameters to the user's endpoint (`src/core/dapps.ts:228`). The method allowlist limits damage, but a site can burn a user's API-key quota or probe a `localhost` node the user has configured.

**I-3.** Neither manifest sets `minimum_chrome_version`, although the code depends on `storage.session.setAccessLevel` (Chrome 102), `documentLifecycle` (106) and the Popover API (114). Both manifest descriptions still read "Unaudited testnet alpha" after mainnet signing was enabled.

**I-4.** `src/browser/handler.ts`, `src/core/status.ts`, the `app:get-status` message type and `isAppStatus` are a leftover prototype that always reports `not-created`. They are still reachable from `background.ts:223`. Harmless, but dead authorization paths are a maintenance risk.

**I-5.** No test anywhere exercises `wallet_addEthereumChain` (confirmed with `grep -rn addEthereumChain tests/`). It is the one dapp method that persistently changes trusted configuration.

## What was not done

- I did not run the Playwright, Selenium or Anvil suites, or install the extension in a browser.
- I did not fuzz viem's EIP-712 encoder or the ABI decoder; those are upstream.
- I did not attempt memory forensics on the exported session key.
- Firefox `documentId` behaviour (L-8) was not verified at runtime.

## Suggested order of work

1. M-1: protect built-in networks from dapp rewrites and add the missing tests.
2. L-2: cache addresses at unlock. Small change, removes a cheap DoS and most key churn.
3. M-2: tolerant feed parsing plus a daily update alarm.
4. L-3 and L-4: approval screen hardening before wider mainnet use.
5. L-5, L-6, L-7, L-9: hygiene items for the next release.
